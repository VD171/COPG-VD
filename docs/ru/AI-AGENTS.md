# ИИ-агенты: поверхность управления

COPG-VD приветствует контрибьюторов-ИИ и агентов, и весь модуль построен так, чтобы им можно было управлять
в безголовом режиме, не скрапя WebUI. Есть две поверхности, и агент, работающий как root (как это делает
WebUI), использует обе:

1. **Файл конфигурации** `/data/adb/COPG-VD/COPG-VD.json` - единственный источник истины. Каждое поле
   профиля и каждая настройка живут здесь, чтение и запись этого файла - это то, как вы меняете то, что
   модуль подделывает.
2. **Точка входа shell** `fingerprint-update.sh` - один скрипт со стабильными глаголами для проверки,
   применения и загрузки профилей.

## Файл конфигурации

`/data/adb/COPG-VD/COPG-VD.json` - это обычный объект JSON. Модуль читает его из внедрённых процессов через
собственное правило SELinux, которое сам поставляет, он не хранит никаких учётных данных. Поставляемый пример
лежит в `module/COPG-VD.json.example` и ежедневно обновляется из новейшего заводского образа Google.

Правила, которым должен следовать агент:

- **Строки используют только двойные кавычки**, как в JSON.
- **Каждое поле необязательно.** Поле, которое не предоставлено, пропускается, и сохраняется собственное
  значение ROM.
- Ключи верхнего уровня, управляющие модулем, - это `scope_mode`, `scope_whitelist`, `scope_blacklist`,
  `motor_drm`, `drm_targets`, `global_fields`, `process_overrides`, объект `COPG-VD` (поля Build), список
  `COPG-VD-Delete` и объект `COPG-VD-Settings` (`resetprop`, `autoupdate`, `spoof_version`). [Справочник по
  конфигурации](CONFIGURATION.md) описывает каждый из них.
- `"spoof_version": "force"` отклоняется, когда поступает из файла на диске, и понижается при чтении, так что
  восстановление старой резервной копии не может тихо снова его взвести. Задавайте политику версии через
  настройки, а не вписывая `force` вручную.
- После редактирования файла запустите **`analyze`** (ниже): файл, который не парсится, заставляет модуль не
  подделывать **ничего**, и об этом говорит только logcat.

Изменённая конфигурация доходит до приложений при следующем старте процесса. Свойства, доставляемые через
`resetprop`, можно применить заново без перезагрузки (`service.sh --props-only`), но поля `android.os.Build.*`
записываются библиотекой Zygisk при старте zygote, поэтому для их доставки в приложения **требуется
перезагрузка**.

## Контракт shell

```
sh /data/adb/modules/COPG-VD/fingerprint-update.sh <verb> [arg]
```

Скрипт печатает строки, читаемые человеком, читаемые машиной начинаются с `status:`. Его код выхода - `0` при
успехе и ненулевой при сбое.

| Глагол | Что делает | Типичный вывод |
|---|---|---|
| `check` | Сравнивает установленный профиль с новейшей upstream-сборкой, ничего не записывает. | `status: update-available` \| `status: up-to-date` \| `status: local-newer` \| `status: no-config` |
| `apply` | Загружает новейший профиль и сливает его в конфигурацию (только поля Build, ваши остальные ключи сохраняются). | `status: applied` \| `status: up-to-date` \| `status: local-newer` \| `status: analyze-red` \| `status: skipped-custom-device` \| `status: failed` |
| `analyze` | Проверяет конфигурацию в её текущем виде (parse, версия против ROM, согласованность fingerprint, неизвестные ключи, даты, props). Печатает отчёт, код выхода отражает находки red/warn. | текстовый отчёт |
| `fetch-index` | Загружает и проверяет подписанный индекс устройств и печатает его (`index.json`). | JSON индекса \| `status: sig-failed` \| `status: download-failed` |
| `fetch <path>` | Загружает `build.prop` одного устройства (путь из индекса, напр. `pixel-9a/latest.prop`) и записывает его поля Build в конфигурацию. | `status: fetched` \| `status: bad-path` \| `status: map-failed` \| `status: write-failed` |
| `sync-settings` | Переносит состояние/конфигурацию из старой плоской раскладки в `/data/adb/COPG-VD/`. | - |
| `migrate` | Разовая миграция конфигурации между версиями модуля. | `status: migrated` \| `status: nothing-to-migrate` |
| `boot` | Автообновление раз за загрузку, предназначено для `service.sh`, не для интерактивного использования. | записывает `update.status` |

Каждая загрузка проверяется перед использованием (единственный загрузчик на устройстве - busybox `wget`,
который не умеет проверять TLS), а обновлятель профиля никогда не идёт назад: upstream-сборка старше
установленной отклоняется. Индекс канала и каждый `.prop` несут отделённую подпись ed25519, которая
проверяется до того, как содержимое будет прочитано.

## Типичные потоки агента

- **Держать профиль свежим:** `check`; если `status: update-available`, то `apply`; затем перезагрузитесь,
  чтобы новые `Build.*` дошли до приложений.
- **Переключиться на другой профиль Pixel:** `fetch-index`, выберите путь устройства из индекса, `fetch
  <path>`, запустите `analyze`, чтобы подтвердить согласованность конфигурации, затем перезагрузитесь.
- **Изменить область или движок:** отредактируйте `scope_mode` (или переключатель движка) в файле
  конфигурации, запустите `analyze`, затем `service.sh --props-only` для изменений, доставляемых через
  свойства, или перезагрузитесь для полей Build.

## Ограждения безопасности

- Изменение конфигурации или применение профиля меняет то, что видит каждое целевое приложение, подтверждайте
  намерение перед записью, как это делает WebUI.
- Никогда не ослабляйте настоящую защиту согласованности: SDK ограничен реальным фреймворком при любой
  политике, manufacturer остаётся в согласии с остальным профилем, а профиль другого устройства отклоняется.
  Это сделано намеренно и не должно обходиться.
- Конфигурация - это поддерживаемая поверхность. Не скрапьте и не автоматизируйте саму WebUI.
