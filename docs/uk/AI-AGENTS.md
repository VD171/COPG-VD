# AI-агенти: поверхня керування

COPG-VD вітає учасників-AI та агентів, і весь модуль побудований так, щоб ним можна було керувати без
інтерфейсу, без скрапінгу WebUI. Існують дві поверхні, і агент, що працює з правами root (як це робить
WebUI), використовує обидві:

1. **Файл конфігурації** `/data/adb/COPG-VD/COPG-VD.json` - єдине джерело істини. Кожне поле профілю і
   кожне налаштування міститься тут, читання й запис цього файлу - це те, як ви змінюєте те, що
   підробляє модуль.
2. **Точка входу в оболонку** `fingerprint-update.sh` - один скрипт зі стабільними дієсловами для
   перевірки, застосування та отримання профілів.

## Файл конфігурації

`/data/adb/COPG-VD/COPG-VD.json` - це звичайний об'єкт JSON. Модуль читає його з ін'єктованих процесів
через спеціальне правило SELinux, яке він постачає сам, він не містить жодних облікових даних. Приклад,
що входить до комплекту, міститься в `module/COPG-VD.json.example` і щодня оновлюється з найновішого
заводського образу Google.

Правила, яких має дотримуватися агент:

- **Рядки використовують лише подвійні лапки**, як у JSON.
- **Кожне поле є необов'язковим.** Поле, яке не надано, пропускається, і зберігається власне значення
  ROM.
- Ключі верхнього рівня, що керують модулем, - це `scope_mode`, `scope_whitelist`, `scope_blacklist`,
  `motor_drm`, `drm_targets`, `global_fields`, `process_overrides`, об'єкт `COPG-VD` (поля Build),
  список `COPG-VD-Delete` та об'єкт `COPG-VD-Settings` (`resetprop`, `autoupdate`, `spoof_version`).
  [Довідник конфігурації](CONFIGURATION.md) документує кожен із них.
- `"spoof_version": "force"` відхиляється, коли надходить із файлу на диску, і знижується під час
  читання, тож відновлення старої резервної копії не може тихо повторно його активувати. Задавайте
  політику версій через налаштування, а не вписуванням `force` вручну.
- Після редагування файлу запустіть **`analyze`** (нижче): файл, який не парситься, призводить до того,
  що модуль не підробляє **нічого**, і лише logcat про це повідомляє.

Змінена конфігурація досягає застосунків під час наступного запуску процесу. Властивості, доставлені
через `resetprop`, можна застосувати повторно без перезавантаження (`service.sh --props-only`), але поля
`android.os.Build.*` записуються бібліотекою Zygisk під час запуску zygote, тож для того, щоб вони
досягли застосунків, **потрібне перезавантаження**.

## Контракт оболонки

```
sh /data/adb/modules/COPG-VD/fingerprint-update.sh <verb> [arg]
```

Скрипт виводить рядки, зрозумілі людині, машиночитані починаються з `status:`. Його код виходу - `0` в
разі успіху і ненульовий у разі збою.

| Дієслово | Що робить | Типовий вивід |
|---|---|---|
| `check` | Порівнює встановлений профіль із найновішою upstream-збіркою, нічого не записує. | `status: update-available` \| `status: up-to-date` \| `status: local-newer` \| `status: no-config` |
| `apply` | Отримує найновіший профіль і зливає його в конфігурацію (лише поля build, інші ваші ключі зберігаються). | `status: applied` \| `status: up-to-date` \| `status: local-newer` \| `status: analyze-red` \| `status: skipped-custom-device` \| `status: failed` |
| `analyze` | Перевіряє конфігурацію як є (парсинг, версія проти ROM, узгодженість fingerprint, невідомі ключі, дати, props). Виводить звіт, код виходу відображає знахідки red/warn. | текстовий звіт |
| `fetch-index` | Завантажує й перевіряє підписаний індекс пристроїв і виводить його (`index.json`). | JSON індексу \| `status: sig-failed` \| `status: download-failed` |
| `fetch <path>` | Завантажує `build.prop` одного пристрою (шлях з індексу, напр. `pixel-9a/latest.prop`) і записує його поля build у конфігурацію. | `status: fetched` \| `status: bad-path` \| `status: map-failed` \| `status: write-failed` |
| `sync-settings` | Переносить стан/конфігурацію зі старого плаского розташування до `/data/adb/COPG-VD/`. | - |
| `migrate` | Одноразова міграція конфігурації між версіями модуля. | `status: migrated` \| `status: nothing-to-migrate` |
| `boot` | Автооновлення один раз за завантаження, призначене для `service.sh`, а не для інтерактивного використання. | записує `update.status` |

Кожне завантаження перевіряється перед використанням (єдиний завантажувач на пристрої - це busybox
`wget`, який не може перевіряти TLS), і оновлювач профілю ніколи не йде назад: upstream-збірка, старіша
за встановлену, відхиляється. Індекс стрічки і кожен `.prop` несуть відокремлений підпис ed25519, який
перевіряється перед читанням вмісту.

## Типові сценарії агента

- **Тримайте профіль свіжим:** `check`; якщо `status: update-available`, `apply`; потім перезавантажте,
  щоб нові `Build.*` досягли застосунків.
- **Перемкніться на інший профіль Pixel:** `fetch-index`, виберіть шлях пристрою з індексу, `fetch
  <path>`, запустіть `analyze`, щоб підтвердити узгодженість конфігурації, потім перезавантажте.
- **Змініть область дії або рушій:** відредагуйте `scope_mode` (або перемикач рушія) у файлі
  конфігурації, запустіть `analyze`, потім `service.sh --props-only` для змін, доставлених через
  властивості, або перезавантажте для полів Build.

## Запобіжники

- Зміна конфігурації чи застосування профілю змінює те, що бачить кожен цільовий застосунок;
  підтвердьте намір перед записом, як це робить WebUI.
- Ніколи не послаблюйте справжній захист узгодженості: SDK обмежений справжнім framework за будь-якої
  політики, виробник залишається в узгодженні з рештою профілю, а профіль для іншого пристрою
  відхиляється. Це зроблено навмисно і не має обходитися.
- Конфігурація - це підтримувана поверхня. Не скрапте і не автоматизуйте сам WebUI.
