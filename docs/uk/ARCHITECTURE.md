# Архітектура

COPG-VD є модулем Zygisk: невелика нативна бібліотека (`libspoof.so`), яку завантажувач Zygisk
впроваджує у zygote і, звідти, у процеси застосунків. Усе, що вона робить, подає
вибрану ідентичність пристрою процесам, які ви націлюєте. Немає застосунку і, окрім
необов'язкового завантаження профілю, немає мережі.

## Життєвий цикл

1. **Старт zygote.** Коли zygote завантажується, завантажувач викликає `onLoad` модуля. Він
   читає `/data/adb/COPG-VD/COPG-VD.json` один раз: конфігурацію області та профіль.
2. **Fork застосунку.** Для кожного застосунку, який форкає zygote, модуль вирішує у
   `preAppSpecialize`, чи цей процес в області:
   - **в основній області** (`playstore` / `global` / `whitelist` / `blacklist`), або
   - **в області DRM** (перелічений у `drm_targets`).
   Якщо він ні там, ні там, модуль **від'єднується** від цього процесу (`dlclose`) і не залишає
   в ньому слідів.
3. **Specialize.** Для процесу, що залишається, рушії застосовуються у `postAppSpecialize`,
   доки процес ще привілейований.

Оскільки fork'и успадковують копію пам'яті zygote за принципом copy-on-write, кожен застосунок стартує з конфігурації,
прочитаної під час завантаження. Модуль перечитує файл для цільового процесу лише коли той справді
змінився, тож щойно запущений чи повторно відкритий застосунок підхоплює відредагований профіль, але рішення про
область приймається під час старту zygote, тож **зміна області, рушіїв чи
`drm_targets` потребує перезавантаження**.

## Рушії

Кожен незалежний і перемикається.

- **Поля Build (`motor_jni`).** Переписує `android.os.Build.*` (і `Build.VERSION.*`)
  у цільовому процесі через JNI, тож код Java читає підмінені значення.
- **Хук властивостей (`motor_prop_hook`).** Подає підмінені системні властивості
  процесу через чистий попроцесний ремап області властивостей (`prop_virtualizer`).
  Це ремап пам'яті, а не хук функції, тож немає відбитка хукнутої функції.
- **resetprop (загальнопристроєвий).** Записує системні властивості за групами: ідентичність, версія,
  стан завантаження, SELinux, adb/usb, анти-емулятор, плюс прохід очищення. Його запускають скрипти
  завантаження. У режимі з областю групи ідентичності та версії залишаються поза (Zygisk доставляє їх
  по процесах), групи завантаження, блокування та SELinux залишаються глобальними, щоб пристрій був узгодженим.
- **DRM / Widevine (`motor_drm`).** Хукає методи `MediaDrm`, що повідомляють рівень безпеки
  Widevine (`getSecurityLevel`, `getPropertyString`), і повертає налаштований
  рівень. Хуки перевіряються на null, тож некоректний профіль деградує плавно замість
  падіння застосунку. `drm_targets` дозволяє цьому рушію працювати на власному списку застосунків, відв'язаному від
  основної області.

## Читання конфігурації

Впроваджений процес працює в домені SELinux zygote, який за замовчуванням не може дістатися до
`/data/adb`. Модуль постачає власне `sepolicy.rule`, щоб це дозволити, і, як запасний варіант,
може читати конфігурацію через свій відкритий каталог модуля (`getModuleDir`), тож він продовжує
працювати навіть якщо збірка Zygisk перестане надавати цей шлях. Файл парситься невеликим
вбудованим парсером JSON (`jsmn`), файл, що не парситься, означає, що модуль не підміняє нічого.

## Підтримання профілю свіжим

`fingerprint-update.sh` оновлює поля build з найновішого заводського образу Google,
з WebUI чи раз на завантаження. Він використовує власний вбудований завантажувач модуля (не `PATH`
`curl`/`wget`), перевіряє кожне значення перед використанням, ніколи не йде назад і відхиляє
профіль, що підмінює інший пристрій. `android.os.Build` записується під час старту zygote, тож
нові значення доходять до застосунків при наступному перезавантаженні. Див. [USER-GUIDE.md](USER-GUIDE.md) для користувацького
боку і [CONFIGURATION.md](CONFIGURATION.md) для полів.

## Чому версія Android не підмінюється за замовчуванням

Підвищення `SDK_INT` / `ANDROID_VERSION` над тим, чим насправді є фреймворк ROM, змушує застосунки
викликати API, яких не існує, що валить застосунки Google і перезавантажує телефон у
softloop. Тому група версії вимкнена за замовчуванням і захищена за
`spoof_version`, і починаючи з v6.19 SDK додатково обмежується значенням справжнього фреймворку в **усіх** політиках (включно з Force), тож навіть профіль із примусово підвищеним SDK не може спричинити softloop (Force усе одно примусово задає рядкові поля версії). Модуль читає справжню версію з `/system/build.prop`, ніколи з
`getprop`, бо `getprop` і є саме те, що він фальсифікує. Див. пастку у
[USER-GUIDE.md](USER-GUIDE.md#the-android-version-trap).
